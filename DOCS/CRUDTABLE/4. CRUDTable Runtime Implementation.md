

# CRUDTable Runtime Implementation

This document captures the current state of the AS500 CRUDTable runtime engine — what was built, how it maps to the spec, design decisions made, and areas to revisit.

---

## 1. What Was Built

A runtime engine that interprets a declarative `CRUDTableConfig` object and auto-generates two screens:

1. **List screen** (subfile) — paginated table with option-based row actions
2. **Form screen** — create/edit form with validation

The engine plugs into the existing AS500 WebSocket router via a fallback pattern: known screens are routed as before, unknown `CRUD_*` screen IDs are handled by the CRUDTable runtime.

### File Layout

```
server/src/
  crudtable/
    types.ts        # All interfaces
    registry.ts     # Config store + screen ID derivation
    context.ts      # CRUDContext <-> session.context mapping
    runtime.ts      # Core engine (build + handle for list & form)
    router.ts       # Integration hooks for index.ts
  configs/
    index.ts        # Registration bootstrap
```

### Changes to Existing Code

Only `server/src/index.ts` was modified — three additions:
1. Import `registerCRUDConfigs` and `handleCRUDScreen`/`buildCRUDScreenForResume`
2. Call `registerCRUDConfigs()` in `startServer()`
3. Default case in both `getCurrentScreenResponse` and the message handler routes through the CRUDTable runtime before falling back to login

Zero changes to existing screens, services, DSL, or client.

## 2. How It Maps to the Spec

### Direct mappings

| Spec concept | Implementation |
|---|---|
| `AdminUIConfig.id` | `CRUDTableConfig.id` — drives screen IDs via `CRUD_{ID}` / `CRUD_{ID}_FORM` |
| `AdminUIConfig.title` | Used in header and form title (`CREATE {TITLE}` / `EDIT {TITLE}`) |
| `services.list/create/update/delete` | `ServiceCall` with `service` object + `method` string + optional `params(context)` |
| `fieldConfigs` | Same structure — `field`, `label`, `form?`, `column?`, `datasource?` |
| `columnBuilder` / `formBuilder` | String arrays referencing fieldConfig keys, same as spec |
| `getInitialValues` | Called on create mode only, receives CRUDContext |
| `actions` | Record-scoped actions auto-numbered from 5 in the subfile option hints |
| `openUI` | Option 9 in the subfile, derives context via `mapContext`, navigates to target config's list screen |
| `BoolExpr` | `boolean \| ((context) => boolean)` — used for `visible`, `disabled`, `required` |
| `Validator` | `(context) => string \| null` — run sequentially, first error wins |

### AS500-specific additions (not in original spec)

| Addition | Reason |
|---|---|
| `length: number` on FieldConfig | AS/400 screens need explicit field widths for the 80-char grid |
| `type?: FieldType` on FieldConfig | Maps to DSL field types (`alpha`, `numeric`, `date`, `password`, `readonly`) |
| `form.uppercase?: boolean` | AS/400 convention for uppercase-only fields |
| `requireAuth` / `requireAdmin` on config | Auth gating per-screen, checked by router before entering runtime |

### Simplifications vs spec

| Spec concept | What we did | Why |
|---|---|---|
| `AdminContext.env` | Not implemented | Single environment (server-side terminal) |
| `context.selection` as ordered array | Selection is set to single record on option entry | Terminal UI is single-select by nature (one opt field per row) |
| `action.scope: 'bulk'` | Not implemented | No multi-select in terminal UI |
| `action.scope: 'global'` | Not implemented yet | Could map to F-keys in future |
| `action.confirm` | Not implemented | No confirmation dialog pattern in AS/400 yet (could add a confirm screen) |
| `datasource` in forms | Loaded eagerly, stored in context | Not yet rendered as selectable options in the form — the data is available but form just shows a text field |
| `ServiceCall.transform` | Not implemented | Context mutation after service call — unclear need so far |

## 3. Key Design Decisions

### Screen ID convention

`CRUD_{ID}` for list, `CRUD_{ID}_FORM` for form. The `CRUD_` prefix makes the fallback routing safe — it will never collide with manually-created screen IDs like `LOGIN`, `MAIN_MENU`, etc.

### Context namespacing

All CRUDContext state is stored in `session.context` with keys like `crud_{configId}_records`, `crud_{configId}_pageOffset`, etc. This prevents collisions between multiple active CRUD configs and with existing non-CRUD screen context (e.g., `timeRegDate`).

### Service call pattern

```typescript
const result = await service[method](params);
```

The `params` function bridges between CRUDContext and whatever the service expects. This keeps service functions unchanged — they don't need to know about CRUDTable.

### Fallback routing (not switch-case registration)

Instead of adding each CRUD screen to the switch statement in `index.ts`, the default case tries `handleCRUDScreen()` first. This means adding a new CRUD screen requires zero changes to `index.ts` — just register the config.

### Form field labels

Auto-generated as `{label} . . . :` to match AS/400 style. The form uses fixed column positions: labels at col 8, fields at col 30.

### Option numbering

Fixed: 2=Edit, 4=Delete, 9=OpenUI. Custom actions auto-number from 5, skipping 9 if openUI is defined. This matches AS/400 convention where option numbers are stable and documented.

## 4. Current Limitations and Known Issues

### Things that need refinement

1. **Datasource rendering in forms** — Datasources are loaded and cached but not rendered as selection lists. The form just shows a text input. For the terminal, this could be an F4 prompt screen showing the datasource values.

2. **No confirmation for delete** — The spec defines `action.confirm` but there's no confirmation step. Delete happens immediately on option 4. Could add a confirm screen or a "press Enter again to confirm" pattern.

3. **cellRenderer output not truncated** — If a cellRenderer returns a string wider than the column width, it could overflow. The subfile DSL truncates, but the runtime should also guard.

4. **No global actions** — Actions with `scope: 'global'` aren't wired to anything. These could map to F-keys (e.g., F5=Refresh, F9=Custom).

5. **Form doesn't preserve input on validation error** — When validation fails, the form rebuilds from editRecord/initialValues, not from what the user typed. The `fieldValues` sent back should use `request.input` values on error.

6. **No page indicator** — The list screen doesn't show "Page X of Y" or record count. Only the standard "More..." indicator from the subfile DSL.

7. **openUI context derivation is minimal** — Only `input` is passed from mapContext to the target. The full CRUDContext isn't reconstructed from derivedCtx — only `input` is seeded.

8. **Action map stored in session.context** — The `crud_{id}_actionMap` is stored in session context for the handler to read. This is a runtime artifact, not part of CRUDContext. Could be cleaner.

9. **buildReturnScreen uses dynamic imports** — When navigating back to a non-CRUD screen (like MAIN_MENU), the runtime dynamically imports screen builders. This works but is fragile if new non-CRUD screens are added.

### Things that work well

- Clean separation: config authors never touch screen rendering or key handling
- The existing DSL (subfile, form, header) does all the heavy lifting
- Auth gating is declarative and consistent
- Pagination works identically to hand-written screens
- Adding a new CRUD screen is ~50 lines of config + 0 lines of router changes

## 5. How to Add a New CRUD Screen

### Step 1: Create the service

Standard service file in `server/src/services/`. Functions should accept simple arguments and return arrays or objects.

```typescript
// server/src/services/customers.ts
export async function getAllCustomers(): Promise<Customer[]> { ... }
export async function createCustomer(data: { name: string, city: string }): Promise<Customer> { ... }
export async function updateCustomer(data: { id: number, name: string, city: string }): Promise<Customer> { ... }
export async function deleteCustomer(id: number): Promise<void> { ... }
```

### Step 2: Create the config

```typescript
// server/src/configs/customers.ts
import type { CRUDTableConfig } from '../crudtable/types.js';
import * as customerService from '../services/customers.js';

export const customersConfig: CRUDTableConfig = {
  id: 'customers',
  title: 'Customer Maintenance',
  requireAuth: true,

  services: {
    list:   { service: customerService, method: 'getAllCustomers' },
    create: { service: customerService, method: 'createCustomer', params: ctx => ctx.values },
    update: { service: customerService, method: 'updateCustomer',
              params: ctx => ({ id: ctx.editRecord!.id as number, ...ctx.values }) },
    delete: { service: customerService, method: 'deleteCustomer',
              params: ctx => ctx.selection[0].id },
  },

  fieldConfigs: {
    name: {
      field: 'name',
      label: 'Name',
      length: 20,
      form: { required: true },
      column: { width: 20 },
    },
    city: {
      field: 'city',
      label: 'City',
      length: 15,
      column: { width: 15 },
    },
  },

  columnBuilder: ['name', 'city'],
  formBuilder: ['name', 'city'],
};
```

### Step 3: Register

```typescript
// server/src/configs/index.ts
import { customersConfig } from './customers.js';
registerConfig(customersConfig);
```

### Step 4: Navigate to it

From mainMenu.ts or any screen:
```typescript
session.screenStack.push('MAIN_MENU');
session.currentScreen = 'CRUD_CUSTOMERS';
```

No other files need changes.

## 7. Testing Strategy (Not Yet Implemented)

For future test coverage:

1. **Unit test the runtime** — Mock a simple config, call `buildListScreen` and `handleList` directly, assert screen output and state transitions.

2. **E2E test a sample config** — Register a test config, navigate to it via main menu, verify list/create/edit/delete cycle.

3. **Template from existing tests** — `tests/time-registration-crud.spec.ts` is the pattern. Copy and adapt for a CRUDTable screen.

## 8. Future Refinement Ideas

- **F4 Prompt screens for datasources** — When a field has a datasource, F4 could open a selection subfile
- **Confirmation screen for delete** — A mini "Are you sure? (Y/N)" screen before destructive actions
- **Column sorting** — Config-driven sort column and direction
- **Filtering** — A filter row above the subfile for narrowing results
- **Bulk actions** — Multi-select via option field (e.g., option 4 on multiple rows before pressing Enter)
- **Global actions as F-keys** — Map `scope: 'global'` actions to configurable F-key bindings
- **Form field grouping** — Visual sections within the form (like AS/400 group jobs)
- **Computed/readonly fields on form** — Show calculated values during create/edit
- **Preserve user input on validation error** — Use request.input values instead of rebuilding from editRecord
