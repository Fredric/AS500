

---

With openUI, you can:

- Chain small UIs together
    
- Build master → detail flows
    
- Compose complex admin systems out of simple screens
    
- Do this **without coupling UIs together**
    

  

Example mental models:

- AS/400 screen chaining
    
- Terminal commands that open sub-menus
    
- “Select row → drill down”
    

---

## What openUI* Does (Conceptually)

1. UI **A** is active
    
2. User selects one or more records
    
3. UI **A** triggers openUI
    
4. A **new context** is created using mapContext
    
5. UI **B** becomes active
    
6. UI **A** is no longer active
    

  

⚠️ Important:

- Context is **copied / derived**, not shared
    
- UI **B cannot mutate UI A’s context**
    
- Only one UI exists at a time
    

---

## **openUI**

##  **Shape**

```
openUI?: {
  id: string
  mapContext: (parentContext: TContext) => TContext
}
```

---

## **id**

```
id: string
```

The id of the **target AdminUIConfig**.

  

This must match the id property of another registered UI config.

  

Example:

```
id: 'userDetails'
```

---

## **mapContext**

```
mapContext: (parentContext) => newContext
```

This is the **most important part**.

  

### **What it does**

- Takes the **current UI’s context**
    
- Produces a **new context** for the next UI
    
- You decide exactly what data is passed forward
    

  

### **What you typically pass**

- IDs from selection
    
- Derived values
    
- Static flags
    
- Anything the next UI needs to operate
    

  

### **What you should NOT do**

- Do not mutate parentContext
    
- Do not rely on side effects
    
- Do not assume UI implementation details
    

---

## **Canonical Example: Master → Detail**

  

### **Users UI**

```
openUI: {
  id: 'userDetails',
  mapContext: parent => ({
    selection: [],
    input: {
      userId: parent.selection[0].id
    }
  })
}
```

### **What’s happening**

- User selects a user
    
- selection[0].id is extracted
    
- New UI receives:
    
    - No selection
        
    - An input parameter (userId)
        
    

---

## **How the Target UI Uses It**

  

In UserDetailsUI:

```
services: {
  list: {
    service: UserService,
    method: 'getUserDetails',
    params: ctx => ({
      userId: ctx.input?.userId
    })
  }
}
```

The second UI does **not** know _who_ opened it.

It only knows:

  

> “I was given a userId in my context.”

  

This is deliberate.

---

## **Terminal-Friendly Mental Model**

  

Think in commands:

```
> users
[1] Alice
[2] Bob

> select 2
> open details
```

Internally:

- selection = [Bob]
    
- openUI maps → { input: { userId: 2 } }
    
- userDetails UI starts
    

  

No routing. No URLs. No components.

Just **state transformation**.

## **Common Patterns**

  

### **1. Passing Multiple IDs (Bulk)**

```
mapContext: parent => ({
  selection: [],
  input: {
    userIds: parent.selection.map(u => u.id)
  }
})
```

---

### **2. Resetting Selection Explicitly**

  

Always recommended.

```
mapContext: parent => ({
  ...parent,
  selection: []
})
```

Why:

- Prevents accidental reuse
    
- Makes flows explicit
    
- Safer for terminal UIs
    

---

### **3. Passing Derived Flags**

```
mapContext: parent => ({
  selection: [],
  input: {
    userId: parent.selection[0].id,
    readOnly: true
  }
})
```

---

### **4. Using with Actions**

  

openUI is often triggered by an **action**:

```
actions: {
  openDetails: {
    label: 'Open details',
    scope: 'record',
    service: noop,
    method: 'noop'
  }
},
openUI: {
  id: 'userDetails',
  mapContext: ...
}
```

(The runtime decides _when_ openUI is invoked.)

---

## What openUI is not

- ❌ Not routing
    
- ❌ Not UI layout
    
- ❌ Not component composition
    
- ❌ Not a modal definition
    

  

It is **pure state transition**.

---

## **Design Rules (Authoring Guide)**

  

When writing openUI:

1. Assume the next UI knows **nothing**
    
2. Pass only what is needed
    
3. Prefer IDs over objects
    
4. Clear selection unless intentional
    
5. Keep mapContext small and obvious
    

  

If someone reads it 6 months later, it should be clear **why** the UI transition exists.

---

## **One-Sentence Definition**

  

> openUI defines a **controlled, one-way transition** from one Admin UI to another by **deriving a new context** from the current one.
