# CRUDTable — Reference

> **Field-by-field, screen-by-screen reference for the CRUDTable runtime.**
> Read **`5. CRUDTable Concept.md`** first if you need the mental model. If you only need to *build* a new screen, **`.cursor/skills/crudtable/SKILL.md`** is the fastest path.
>
> This file is derived from the actual implementation in `server/src/crudtable/*` and the three registered configs in `server/src/configs/*`.

## 1. Request flow

```
Client keypress
      │
      ▼
index.ts message switch ──default──► router.ts handleCRUDScreen()
                                           │
                                           ├─ auth / admin / permission gate
                                           │
                                           ▼
                                     runtime.ts handleList | handleForm | handleDeleteConfirm
                                           │
                                           ├─ loadContext(session, configId)
                                           ├─ config.services.* via callService(svc, method, params(ctx))
                                           ├─ mutate CRUDContext
                                           ├─ saveContext(session, configId, ctx)
                                           │
                                           ▼
                                     build{List|Form|DeleteConfirm}Screen
                                           │
                                           ├─ build DSL elements (header, subfile/form, listHeader extras)
                                           ├─ render(screenDef, values, { message, messageType, user })
                                           │
                                           ▼
                                     ScreenResponse (rows, fields, navigation, statusLine)
```

## 2. Context model (`CRUDContext`)

Everything the runtime needs between requests lives in a `CRUDContext`, stored in `session.context` under namespaced keys (`crud_{configId}_*`). The runtime serialises and reloads it on every request.

```ts
interface CRUDContext {
  records: Record<string, unknown>[];            // Last `list` result
  selection: Record<string, unknown>[];          // Ordered selection (terminal: max 1 entry)
  values: Record<string, string>;                // Form submission values (raw strings)
  input: Record<string, unknown>;                // Caller-supplied context (e.g. { userId, date })
  user: string | null;                           // Session username
  formMode: 'create' | 'edit' | null;
  editRecord: Record<string, unknown> | null;    // Record being edited
  pendingDeleteRecord: Record<string, unknown> | null; // Record awaiting delete confirmation
  pageOffset: number;                            // Subfile pagination offset (0, 12, 24, …)
  datasources: Record<string, Record<string, unknown>[]>; // Lookup data keyed by fieldKey
}
```

### Rules

- **Only the runtime mutates `CRUDContext` fields.** Config functions (`params`, validators, `listKeys.handler`, `listHeader`, `getInitialValues`, `mapContext`, `cellRenderer`) read it; `listKeys.handler` is the one place that may mutate fields it owns (typically `input` and `pageOffset`).
- **`input` is the channel for caller-provided context.** The navigating screen seeds `session.context['crud_{id}_input']` *before* setting `currentScreen`. `openUI.mapContext` may return `{ input: {...} }` to seed the target.
- **Context is cleared on `F3`/`F12` exit** from the list (`clearContext`) but preserved across `openUI` transitions — the runtime only seeds the new target's `input`.
- **Datasources are lazily loaded once per context.** Every list/form build calls `loadDatasources`, which skips any already present in `ctx.datasources`.

## 3. `CRUDTableConfig`

Canonical shape as implemented in `server/src/crudtable/types.ts`.

```ts
interface CRUDTableConfig {
  id: string;                 // Unique; drives screen IDs
  title: string;              // Shown uppercased in headers

  // Access gates — evaluated BEFORE any runtime code runs
  requireAuth?: boolean;      // Default: true (set false to allow unauthenticated)
  requireAdmin?: boolean;     // Require session.isAdmin
  requirePermission?: string; // Permission key required to access the screen at all

  services: {
    list:    ServiceCall;     // Required
    create?: ServiceCall;     // Omitting disables F6/N and the create flow
    update?: ServiceCall;     // Omitting disables option 2
    delete?: ServiceCall;     // Omitting disables option 4 and the 'd' shortcut
  };

  getInitialValues?: (context: CRUDContext) => Record<string, string>;

  fieldConfigs: Record<string, FieldConfig>;

  columnBuilder: string[];    // Ordered keys into fieldConfigs — list columns
  formBuilder:   string[];    // Ordered keys into fieldConfigs — form fields

  actions?:  Record<string, ActionConfig>;   // Currently only scope:'record' is wired
  openUI?:   OpenUIConfig;                   // Cross-config navigation

  listKeys?: Record<string, ListKeyConfig>;  // Custom F-key handlers on the list
  listHeader?: (context: CRUDContext) =>
    Array<{ row: number; col: number; content: string }>; // Dynamic list header text

  navigation?: {
    primaryAction?: 'edit' | 'open';   // What Enter does on a focused row
    shortcuts?: Array<{ key: string; option: string | number; label: string }>;
  };
}
```

### 3.1 `ServiceCall`

```ts
interface ServiceCall {
  service: Record<string, Function>;             // A module (import * as X) or plain object
  method: string;                                // Function name within `service`
  params?: (context: CRUDContext) => unknown;    // Built at call time; passed as single arg
  requirePermission?: string;                    // Per-operation permission key
}
```

- If `params` is omitted, `list` is called with no argument; `create`/`update` fall back to `ctx.values` (raw form strings).
- The service is invoked as `service[method](params)` — always with a single argument or none.
- A rejected promise surfaces as an error message; the record is not mutated.

### 3.2 `FieldConfig`

```ts
interface FieldConfig {
  field: string;          // Property name on the record AND the form-field name sent by the client
  label: string;          // Column header, form label, delete-confirm line
  length: number;         // REQUIRED. Form input width; column width fallback.
  type?: FieldType;       // 'alpha' | 'numeric' | 'date' | 'password' | 'readonly'

  staticOptions?: Array<{ value: string; display: string }>; // Inline select options
  datasource?: DatasourceConfig;                              // Service-driven select

  form?: {
    type?: FieldType;                  // Overrides outer `type` for the form
    visible?: BoolExpr;                // false → skipped entirely
    disabled?: BoolExpr;               // true  → rendered readonly, excluded from submit values
    required?: BoolExpr;               // Enforced by built-in required check
    uppercase?: boolean;               // Auto-uppercase the value
    validators?: Validator[];          // Run after required-check; first error wins
    hint?: string;                     // Grey text rendered to the right of the field
    formValue?: (ctx: CRUDContext, rawValue: unknown) => string; // Map backend value → display string on edit
  };

  column?: {
    width?: number;                    // Overrides `length` for the list column
    align?: 'left' | 'right' | 'center';
    cellRenderer?: (ctx: CRUDContext, record: Record<string, unknown>, datasource?: Record<string, unknown>[]) => string;
  };
}

type BoolExpr  = boolean | ((context: CRUDContext) => boolean);
type Validator = (context: CRUDContext) => string | null;   // null = valid
type FieldType = 'alpha' | 'numeric' | 'date' | 'password' | 'readonly';
```

### 3.3 `DatasourceConfig`

```ts
interface DatasourceConfig {
  service: Record<string, Function>;
  method: string;
  params?: (context: CRUDContext) => unknown;
  valueField: string;      // Property in each lookup row holding the value
  displayField: string;    // Property in each lookup row holding the display label
}
```

Datasources are eagerly loaded once per context. They are attached to the rendered form field as `options: [{value, display}]`. The client renders options as a select dropdown. `cellRenderer` on the same field's `column` receives the full `CRUDContext` as its first argument (so the renderer can be context-aware) and the datasource rows as its third argument so it can resolve IDs to labels.

> **MCP/REST note**: `ctx.datasources` is always `{}` in synthetic (MCP/REST) contexts — datasources are only loaded during the terminal screen build cycle. Do not rely on datasource lookups inside `cellRenderer`, `formValue`, validators, or `BoolExpr` functions that run in both paths.

### 3.4 `ActionConfig`

```ts
interface ActionConfig {
  label: string;
  scope: 'global' | 'record' | 'bulk';           // Only 'record' is wired
  service: Record<string, Function>;
  method: string;
  params?: (context: CRUDContext) => unknown;
  visible?: BoolExpr;                            // Type-level only (not honoured yet)
  confirm?: { message: string | ((ctx: CRUDContext) => string) }; // Type-level only
}
```

- **Record-scoped actions** get option numbers starting at `5`, skipping `9` if `openUI` is defined.
- On selection: `ctx.selection = [record]` → `service[method](params(ctx))` → clear selection → re-render list with the action's label + " completed" as an info message. Errors show "{label} failed".

### 3.5 `OpenUIConfig`

```ts
interface OpenUIConfig {
  id: string;                                           // Target config id
  mapContext: (parentContext: CRUDContext) => Partial<CRUDContext>;
}
```

- Occupies **option 9** on every row.
- On trigger: set `parent.selection = [record]` → call `mapContext(parent)` → push parent list onto `screenStack` → set `currentScreen = CRUD_{TARGET_ID}` → seed **only** `session.context['crud_{targetId}_input'] = derivedCtx.input`.
- Other fields returned from `mapContext` are currently ignored.

### 3.6 `ListKeyConfig`

```ts
interface ListKeyConfig {
  label: string;
  handler: (ctx: CRUDContext) => Promise<void>;
}
```

- Keyed by request key name (`'F7'`, `'F8'`, any valid client key).
- Invoked after auth gates, before the list rebuilds. The runtime calls `saveContext` after the handler.
- Label is shown in the status line (`F7` displays as `←`, `F8` displays as `→`; other keys display as-is).

### 3.7 `listHeader`

```ts
listHeader?: (context: CRUDContext) => Array<{ row: number; col: number; content: string }>
```

Called on every list build. Returns static-text elements rendered above the subfile. Rows 1–6 are safe (the subfile header is at row 7). See `timeRegV2.ts` for a working example.

### 3.8 `navigation`

Purely client-side hints. Emitted back in `ScreenResponse.navigation.list`:

| Field | Effect |
|---|---|
| `primaryAction: 'edit'` | Enter on a focused row fills `opt_N='2'` and sends ENTER (default when `update` exists) |
| `primaryAction: 'open'` | Enter on a focused row fills `opt_N='9'` and sends ENTER |
| `shortcuts[]` | Extra single-letter shortcuts mapped to option numbers. The runtime also auto-adds `{ key: 'd', option: '4' }` when a delete service is wired, and shortcuts for every record action. |

## 4. Access control integration

CRUDTable consumes the project's RBAC system (see `ACCESS.md`).

### 4.1 Screen-level gating (`router.ts`, before runtime)

Checked in order; the first failure short-circuits:

1. `requireAuth` (default `true`) → unauthenticated users redirected to `LOGIN`.
2. `requireAdmin` → non-admins redirected to `LOGIN` with "Access denied. Admin privileges required."
3. `requirePermission` → users without the key redirected to `MAIN_MENU` with "Access denied. Insufficient permissions."

### 4.2 Operation-level gating (`ServiceCall.requirePermission`)

`create`, `update`, `delete` can each declare a permission key. The runtime calls `hasPermission(session, key)` at three points:

- When building the list → unavailable operations are not advertised in option hints or shortcuts.
- When handling an option → forbidden operations return an "Access denied: cannot {edit|delete|create} records" error.
- When submitting a form → forbidden operations return the same denied message.

> Record actions (`actions.{key}.service`) do **not** currently consult `ServiceCall.requirePermission`. Use screen-level or per-service CRUD gating for now.

## 5. List screen (`CRUD_{ID}`)

### Layout (80×24)

```
Row 1       Standard header — AS500 SYSTEM / {TITLE} / date / time / user
Row 5       Optional listHeader(ctx) text elements
Row 7       Subfile header row:  "Opt | col1 | col2 | col3 | …"
Row 8       Separator (drawn by DSL subfile)
Rows 9–20   Data rows (page size 12).  First column is `opt_N` input.
Row 24      Status line (auto-built, truncated to 80 chars)
```

### Columns

First column is always the option input: `Opt` width 3, field names `opt_0 … opt_11`. Remaining columns come from `columnBuilder` in order, using `column.width ?? length` and optional `cellRenderer`.

### Option assignments

(Only advertised if the service is wired AND the user holds the required permission.)

| Option | Meaning | Wired when |
|---|---|---|
| `2` | Edit | `services.update` exists |
| `4` | Delete → delete-confirm screen | `services.delete` exists |
| `9` | OpenUI | `openUI` defined |
| `5, 6, 7, 8, 10, …` | Record actions, auto-numbered from 5, skipping 9 if openUI exists | `actions[*].scope === 'record'` |

### Key handling

| Key (`request.key`) | Behaviour |
|---|---|
| `ENTER` | Scan `opt_0 … opt_{N-1}` for first non-blank, dispatch accordingly |
| `F6` (also client `n`/`N` → F6) | Start create flow — push list to stack, go to form |
| `F3` / `F12` (client `Escape` → F3) | Pop `screenStack`, clear this CRUD's context, render return screen |
| `PAGEUP` / `PAGEDOWN` | Move `pageOffset` by 12, clamped |
| Any key in `listKeys` | Invoke handler; re-render |

### Status line composition

Ordered parts (truncated to 80 chars):

```
[Enter=Edit | Enter=Open]  D=Delete  {shortcut.label}…  Esc=Exit  N=New  {listKey.label}…
```

### `ScreenResponse.navigation.list` metadata

```ts
navigation: {
  type: 'list',
  list: {
    dataStartRow,         // 9 (LIST_START_ROW 7 + 2)
    dataRowCount,         // Rows on this page (0..12)
    totalRecords,
    pageOffset,
    hasMore, hasPrev,
    optFieldPrefix: 'opt',
    primaryAction,        // '2' | '9' | ''
    shortcuts,            // [{ key, option, label }, ...]
  },
}
```

## 6. Form screen (`CRUD_{ID}_FORM`)

Title becomes `CREATE {TITLE}` or `EDIT {TITLE}` depending on `crudCtx.formMode`.

### Field sourcing

- **Create**: `fieldValues = getInitialValues(ctx) ?? {}`
- **Edit**: for each `formBuilder` key, value comes from `editRecord[fc.field]`, optionally through `form.formValue(ctx, raw)`.

### Rendering each `formBuilder` entry

1. If `form.visible` evaluates to `false`, the field is omitted entirely.
2. `disabled` → field type forced to `'readonly'`; values from this field are discarded on submit.
3. `required` flows to the DSL `FieldDef` **and** is enforced by the runtime.
4. Field type resolves as `form.type ?? fc.type ?? 'alpha'`.
5. Rows render at label col 8, field col 30, starting row 7. Labels auto-suffixed with ` . . . :`.
6. `staticOptions` or `datasource` → `options: [{value, display}]` attached to the rendered field (client renders dropdown).
7. `form.hint` → grey text at column `30 + length + 2` on the same row.

### Key handling

| Key | Behaviour |
|---|---|
| `F3` / `F12` | Cancel form; clear `formMode`/`editRecord`; return to list |
| `ENTER` | Validate → submit |

### Submit flow

1. For every visible, non-disabled field: read `request.input[fc.field]`, `.trim()`, store in `ctx.values`.
2. Required check (`formBuilder` order). First missing required → rebuild form with `"{label} is required"` error.
3. Run each field's `validators` (`formBuilder` order). First non-null return → rebuild form with that message.
4. Call `services.create` or `services.update` (after the per-service `requirePermission` check). Params are `svc.params?.(ctx) ?? ctx.values`.
5. Success: clear `formMode`/`editRecord`/`values`; pop `screenStack`; list with `"Record created"` / `"Record updated"` info.
6. Thrown error: rebuild form with `error.message` (or a generic fallback) as an error message.

### Relations (edit form only)

`config.relations?: RelationConfig[]` adds single-key hotkeys to the **edit form** that navigate to the list screen of another registered CRUDTable, scoped to the currently edited parent record. This is the declarative answer to "from a motorcycle's edit form, press `M` to see that bike's mods".

**`RelationConfig` shape** (see `server/src/crudtable/types.ts` for full JSDoc):

```ts
interface RelationConfig {
  label: string;          // 'Mods' — shown in the form status bar
  actionKey: string;      // 'M'   — single key, case-insensitive compare
  targetConfigId: string; // 'mods' — CRUDTableConfig.id of the child
  mapInput: (ctx: CRUDContext) => Record<string, unknown>;
}
```

**Runtime behaviour.** When the user presses `actionKey` while `formMode === 'edit'` and `editRecord` is non-null:

1. Resolve the child via `registry.getConfig(targetConfigId)` — an unknown id silently no-ops.
2. `session.context['crud_' + targetConfigId + '_input'] = mapInput(ctx)` — this is what the child reads via `ctx.input` in its `services.list.params` / mutation params. `mapInput` receives the full parent `CRUDContext`, so it can read `ctx.editRecord` (the parent record) plus any other context it needs.
3. Push the **parent form** screen ID onto `session.screenStack` (so Esc from the child list or its own form returns to the parent form in place).
4. Set `session.currentScreen` to the child list and render it via `buildListScreen(targetConfig, session)`.

Relations are **never active on the create form** (where `editRecord` is `null`). On create, the hotkeys are rendered in the status bar but pressing them does nothing — the user must save first.

**Form status bar.** Relations are appended after `Esc=Back`:

```
Esc=Back  M=Mods  S=Services
```

Each relation also shows up as an entry in `ScreenResponse.navigation.form.actions` so the client can bind the key.

**Child config requirements.**

- Registered in `server/src/configs/index.ts`.
- `services.list.params(ctx)` reads scoping from `ctx.input` using the same keys produced by `mapInput` (e.g. `ctx.input.motorcycleId`).
- `services.create` / `update` / `delete` echo those scoping keys back into the mutation so orphaned rows can't be created via the child's own create flow.
- Typically `listHeader(ctx)` shows the parent label (`ctx.input.motorcycleLabel`) so the user knows which parent they're scoped to.

See `server/src/configs/motorcyclesConfig.ts` (parent with `Mods` + `Services` relations) together with `modsConfig.ts` / `servicesPerformedConfig.ts` for the canonical example.

**Constraints / pitfalls.**

- `actionKey` must not collide with `Enter` (submit), `F3` / `F12` / `Escape` (back), or any other handler on the form. Uppercase letters (`M`, `S`, `L`…) are the safe choice.
- Relations don't enforce permissions themselves — the **child** config's `requireAuth` / `requirePermission` gate still runs on the list screen. If the user lacks access, they'll hit the child's permission failure after navigation.
- `mapInput` is called synchronously with the full parent `CRUDContext` (read `ctx.editRecord` to get the parent record). It must not mutate the record or any other context field.
- The parent's `CRUDContext` is saved (`saveContext`) before navigation, so returning to it (Esc) restores `formMode: 'edit'` with the same `editRecord`.

## 7. Delete confirmation screen (`CRUD_{ID}_DELETE_CONFIRM`)

Entered from option `4` on the list.

- Header: `CONFIRM DELETE - {TITLE}`
- "The following record will be permanently deleted:"
- One line per `columnBuilder` entry (`{label} . . . : {value}`)
- Single 1-char uppercase input `confirm`

| Key | Behaviour |
|---|---|
| `F3` / `F12` / `ESCAPE` | Cancel; pop stack; list with "Delete cancelled" |
| `ENTER` with `confirm !== 'Y'` | Treated as cancel |
| `ENTER` with `confirm === 'Y'` | Call `services.delete`; list with `"Record deleted"` or `"Failed to delete record"` |

## 8. Client UX contract (for any list screen)

The client (`client/src/components/Terminal.tsx` + `useTerminal.ts`) consumes `ScreenResponse.navigation.list`:

- Arrow Down/Up → move focus; auto-page at the edges.
- `Enter` on a focused row → fill `opt_N = primaryAction`, send `ENTER`.
- `d` (or any `shortcuts[].key`) on a focused row → fill `opt_N = shortcut.option`, send `ENTER`.
- `n` / `N` anywhere on the list → send `F6`.
- `Escape` → sent as `F3`.
- Mouse click: select; double-click: select + trigger `primaryAction`.
- Tab / Shift+Tab: move between data rows.

Nothing here is CRUDTable-specific — any screen emitting a `navigation.type === 'list'` block gets the same UX.

## 9. Recipe: adding a new CRUD screen

### Step 1 — Services

Plain functions in `server/src/services/thingService.ts`. Each accepts a single argument (usually an object) and returns arrays/records.

```ts
export async function listThings(params?: { filter?: string }): Promise<Thing[]> { … }
export async function createThing(input: { name: string; cityId: number }): Promise<Thing> { … }
export async function updateThing(input: { id: number; name: string; cityId: number }): Promise<Thing> { … }
export async function deleteThing(id: number): Promise<void> { … }
```

### Step 2 — Config

```ts
// server/src/configs/things.ts
import type { CRUDTableConfig } from '../crudtable/types.js';
import * as thingService from '../services/thingService.js';
import * as cityService from '../services/cityService.js';

export const thingsConfig: CRUDTableConfig = {
  id: 'things',
  title: 'Things',
  requireAuth: true,
  requirePermission: 'things:read',

  services: {
    list:   { service: thingService, method: 'listThings' },
    create: { service: thingService, method: 'createThing',
              requirePermission: 'things:write',
              params: ctx => ({ name: ctx.values.name, cityId: Number(ctx.values.cityId) }) },
    update: { service: thingService, method: 'updateThing',
              requirePermission: 'things:write',
              params: ctx => ({ id: ctx.editRecord!.id as number,
                                name: ctx.values.name,
                                cityId: Number(ctx.values.cityId) }) },
    delete: { service: thingService, method: 'deleteThing',
              requirePermission: 'things:write',
              params: ctx => ctx.selection[0].id as number },
  },

  fieldConfigs: {
    name: { field: 'name', label: 'Name', length: 20,
            form: { required: true }, column: { width: 20 } },
    city: { field: 'cityId', label: 'City', length: 4,
            datasource: { service: cityService, method: 'listCities',
                          valueField: 'id', displayField: 'name' },
            form: { required: true },
            column: { width: 18,
                      cellRenderer: (_ctx, r, ds) =>
                        ds?.find(c => c.id === r.cityId)?.name ?? '' } },
  },

  columnBuilder: ['name', 'city'],
  formBuilder:   ['name', 'city'],
};
```

### Step 3 — Register

```ts
// server/src/configs/index.ts
import { thingsConfig } from './things.js';

export function registerCRUDConfigs(): void {
  …
  registerConfig(thingsConfig);
}
```

### Step 4 — Expose in the menu tree

CRUD screens are reached through the central menu tree at `server/src/menus/menuTree.ts`, not by setting `session.currentScreen` from a screen handler. Add a `CrudNode` under the right parent menu:

```ts
// server/src/menus/menuTree.ts
import { thingsConfig } from '../configs/thingsConfig.js';
import { initThingsContext } from '../configs/thingsConfig.js'; // optional

{
  type: 'crudtable',
  key: 'things',
  name: 'Things',
  requirePermission: PERMISSIONS.THINGS_READ,
  configId: 'things',              // matches thingsConfig.id
  initContext: initThingsContext,  // optional — seeds session.context.crud_things_input
}
```

The generic menu runtime (`server/src/menus/menuRuntime.ts`) filters the item by `requirePermission` / `requireAdmin`, pushes the parent menu onto `session.screenStack`, `await`s `initContext(session)`, and then dispatches to `CRUD_{ID_UPPERCASE}`. If the list needs per-user filtering, `initContext` is the correct (and only) place to seed it.

**No other files need to change.** No edits to `server/src/index.ts`, `server/src/screens/mainMenu.ts`, or any hand-written screen handler.

## 11. Permissions quick reference

```ts
// server/src/services/access.ts
PERMISSIONS = {
  TIME_REG_READ:   'time_reg:read',
  TIME_REG_WRITE:  'time_reg:write',
  USER_MGMT_READ:  'user_mgmt:read',
  USER_MGMT_ADMIN: 'user_mgmt:admin',
  SYS_ADMIN:       'sys:admin',
};

hasPermission(session, key) => boolean
```

Roles (`user`, `superuser`, `aiagent`, `admin`) carry default permission sets; admins hold every permission. Permissions are loaded at login and cached on the session as `Set<string>`. Full model is in `ACCESS.md`.

## 12. Known limitations

Current state of the implementation (not blockers — intentional simplifications):

| Area | Status |
|---|---|
| `action.scope: 'global'` and `'bulk'` | Type exists; runtime only dispatches `'record'`. |
| `action.confirm` | Type exists; runtime does not show a confirmation. (CRUD delete has its own dedicated confirmation screen.) |
| Multi-select on the list | Not implemented — terminal has one `opt_N` per row; `selection` is always a single-element array. |
| Custom-action permission gating | Record actions don't check `requirePermission` (CRUD services do). |
| Form input preservation on validation error | Form is rebuilt from `editRecord` or `initialValues`, not from the user's last input. |
| Page indicator | None beyond the DSL's built-in "More..."; `navigation.list.totalRecords`/`pageOffset` is emitted for clients that want to render one. |
| `openUI` context derivation | Only `derivedCtx.input` is seeded on the target; other `mapContext` fields are ignored. |
| `ServiceCall.transform` from the original spec | Not implemented. |
| `CRUDContext.env` from the original spec | Not implemented (single environment). |
