# AdminUIConfig – TypeScript Configuration Object Documentation

This document describes the **main configuration object** used to define an Admin UI screen.

It is intended for **developers authoring configs**, not runtime implementers.
UI framework details are intentionally omitted.

---

## AdminUIConfig<TRecord, TContext>

```ts
export interface AdminUIConfig<TRecord, TContext> {
  id: string
  title: string

  services: {
    list: ServiceCall<TContext>
    create: ServiceCall<TContext>
    update: ServiceCall<TContext>
    delete: ServiceCall<TContext>
  }

  getInitialValues?: (context: TContext) => Partial<TRecord>

  fieldConfigs: Record<string, FieldConfig<TRecord, TContext>>

  columnBuilder: string[]
  formBuilder: string[]

  actions?: Record<string, ActionConfig<TContext>>

  openUI?: OpenUIConfig<TContext>
}
````

---

## **Top-Level Properties**

---

### **id: string**

### **(required)**

  

Unique identifier for this UI.

  

**Why it exists**

- Used for routing, navigation, and composition
    
- Used when opening this UI from another UI
    
- Must be stable and unique across the application
    

  

**Example**

```
id: 'users'
```

---

### **title: string**

### **(required)**

  

Human-readable title of the UI.

  

**Why it exists**

- Displayed by UI (header, window title, terminal heading, etc.)
    
- Not used for logic
    

  

**Example**

```
title: 'Users'
```

---

## **services**

##  **– Data & Mutation Wiring**

  

Defines **how the UI interacts with the backend**.

  

CRUD is implicit and always expected.

```
services: {
  list: ServiceCall<TContext>
  create: ServiceCall<TContext>
  update: ServiceCall<TContext>
  delete: ServiceCall<TContext>
}
```

### **Why services are explicit**

- Keeps UI logic generic
    
- Allows full backend freedom
    
- Keeps config portable across UI types (web / terminal)
    

---

### **services.list**

  

Fetches records to display.

  

**Requirements**

- Must return an array of records
    
- Can read from context
    
- Should not assume UI shape
    

  

**Example**

```
list: {
  service: UserService,
  method: 'getAllUsers',
  params: ctx => ({
    includeDisabled: true
  })
}
```

---

### **services.create**

  

Creates a new record.

  

**Rules**

- Receives full context
    
- Uses getInitialValues + form values
    
- Must return the created record
    

  

**Example**

```
create: {
  service: UserService,
  method: 'createUser'
}
```

---

### **services.update**

  

Updates an existing record.

  

**Rules**

- Always operates on context.selection[0]
    
- Full record is passed
    
- Must return the updated record
    

  

**Example**

```
update: {
  service: UserService,
  method: 'updateUser'
}
```

---

### **services.delete**

  

Deletes selected records.

  

**Rules**

- Operates on context.selection
    
- Confirmation is handled elsewhere
    
- May return nothing
    

  

**Example**

```
delete: {
  service: UserService,
  method: 'deleteUsers'
}
```

---

## **getInitialValues?**

```
getInitialValues?: (context: TContext) => Partial<TRecord>
```

Provides **default values when creating a new record**.

  

**Important rules**

- Called **only on create**
    
- Never used for edit
    
- Read-only access to context
    

  

**Why it exists**

- Keeps defaults out of UI code
    
- Allows context-aware defaults
    

  

**Example**

```
getInitialValues: ctx => ({
  stateId: ctx.input?.defaultStateId ?? 1
})
```

---

## **fieldConfigs**

##  **– Field Definitions**

  

Defines **all known fields** for this UI.

  

Each entry:

- Represents a single logical field
    
- Can be used in forms and/or columns
    
- Is referenced by name in builders
    

```
fieldConfigs: Record<string, FieldConfig<TRecord, TContext>>
```

---

### **FieldConfig Shape**

```
{
  field: keyof TRecord
  label: string

  datasource?: DatasourceConfig<TContext>

  form?: {
    type: string
    visible?: BoolExpr<TContext>
    disabled?: BoolExpr<TContext>
    required?: BoolExpr<TContext>
    validators?: Validator<TContext>[]
  }

  column?: {
    cellRenderer?: (
      record: TRecord,
      datasource?: any[]
    ) => string | number
  }
}
```

---

### **field**

  

The **property name on the record object**.

  

**Why**

- Defines how data maps to backend records
    
- Services only deal in raw values
    

```
field: 'stateId'
```

---

### **label**

  

Human-readable name.

  

Used by UI for:

- Column headers
    
- Form labels
    
- Terminal prompts
    

```
label: 'State'
```

---

### **datasource?**

  

Used for **lookup values** (selects, rendering IDs).

  

**Rules**

- Eager-loaded
    
- Free-form records
    
- UI decides filtering/search
    

```
datasource: {
  service: UserService,
  method: 'getStates',
  valueField: 'id',
  displayField: 'name'
}
```

---

### **form?**

  

Describes how this field behaves in **add/edit UI**.

  

#### **type**

UI-specific input hint (e.g. text, select, number).

  

#### **visible**

#### **,** 

#### **disabled**

#### **,** 

#### **required**

- Boolean or (context) => boolean
    
- Same signature everywhere
    
- No side effects
    

```
required: ctx => ctx.values?.role !== 'guest'
```

#### **validators**

Array of validation functions.

```
validators: [
  ctx => ctx.values?.name ? null : 'Name is required',
  ctx => ctx.values?.name?.length > 50 ? 'Too long' : null
]
```

---

### **column?**

  

Describes how this field appears in list views.

  

#### **cellRenderer**

- Receives record and datasource
    
- Returns text or number
    
- Used for formatting and lookups
    

```
cellRenderer: (record, states) =>
  states?.find(s => s.id === record.stateId)?.name ?? ''
```

---

## **columnBuilder**

```
columnBuilder: string[]
```

Defines **which fields appear in the list** and in what order.

- References keys in fieldConfigs
    
- UI decides how to render
    

```
columnBuilder: ['name', 'state']
```

---

## **formBuilder**

```
formBuilder: string[]
```

Defines **which fields appear in create/edit forms** and order.

- References keys in fieldConfigs
    
- UI decides layout
    

```
formBuilder: ['name', 'state']
```

---

## **actions?**

##  **– Custom Actions**

  

Defines **non-CRUD actions**.

```
actions?: Record<string, ActionConfig<TContext>>
```

Used for:

- Record actions
    
- Bulk actions
    
- Global actions
    

  

CRUD actions are always implicit.

---

### **ActionConfig Shape**

```
{
  label: string
  scope: 'global' | 'record' | 'bulk'

  service: any
  method: string
  params?: (context) => any

  visible?: BoolExpr<TContext>

  confirm?: {
    message: string | ((context) => string)
  }
}
```

---

### **Example Action**

```
resetPassword: {
  label: 'Reset password',
  scope: 'record',
  service: UserService,
  method: 'resetPassword',
  confirm: {
    message: ctx =>
      `Reset password for ${ctx.selection[0].name}?`
  }
}
```

---

## **openUI?**

##  **– UI Composition**

  

Defines navigation to another UI with a **derived context**.

```
openUI?: {
  id: string
  mapContext: (parent: TContext) => TContext
}
```

**Rules**

- Creates a new context
    
- Parent context is not mutated
    
- Only one UI active at a time
    

  

**Example**

```
openUI: {
  id: 'userDetails',
  mapContext: parent => ({
    ...parent,
    input: {
      userId: parent.selection[0].id
    }
  })
}
```

---

## **Summary**

  

The AdminUIConfig object:

- Fully defines a UI screen
    
- Is executable but predictable
    
- Avoids UI coupling
    
- Is portable to terminals
    
- Keeps business logic out of UI components
