# CRUDTable — Concept

> **The mental model of CRUDTable.**
> Read this first. Then go to **`6. CRUDTable Reference.md`** for the field-by-field reference, or to **`.cursor/skills/crudtable/SKILL.md`** for the fast-path recipe an agent should follow when asked to build a new CRUD screen.

---

## 1. What CRUDTable is

**A declarative runtime for CRUD screens.**

A developer writes a single TypeScript object (`CRUDTableConfig`) that declares:

- The backend services for list / create / update / delete
- The fields (shape, label, length, validation, datasources)
- Which fields appear in the list (`columnBuilder`) and which in the form (`formBuilder`)
- Optional custom record actions, cross-screen navigation, access-control gates, and per-screen keyboard extensions

From that one config, the runtime **auto-generates three screens**:

1. A **paginated list** with option-column row actions, keyboard/mouse row navigation, and dynamic status-line hints
2. A **create/edit form** with validation, select dropdowns, required handling, and visible/disabled/required expressions
3. A **delete confirmation** that requires typing `Y` to proceed

The authoring experience is: ~50–150 lines of config + plain-function services → full CRUD screen. Zero edits to the router, the DSL, or the client.

## 2. What it is NOT

- **Not a schema generator.** You explicitly list columns and form fields. We want intent to be visible in the config, not inferred from types or reflected from the DB.
- **Not a router.** It plugs into the existing AS500 WebSocket router as a default-case fallback on `CRUD_*` screen IDs.
- **Not UI-bound.** The config has zero references to pixels, the DOM, React, or specific DSL elements. The one mild exception — `FieldConfig.length` and the `FieldType` enum — is portable with trivial mapping.
- **Not multi-select.** `selection` is typed as an array for future-proofing, but the terminal runtime only ever puts one record into it.
- **Not magic.** Everything the runtime does is traceable: one file handles each screen (list / form / delete-confirm), and each function is ~50 lines.

## 3. Why it exists — the UI-agnostic principle

CRUDTable is the **behavior layer**. The presentation layer is swappable.

```
            ┌──────────────────────────────────────────────┐
            │               CRUDTableConfig                 │
            │  (services, fieldConfigs, validators, actions) │
            └───────────────────┬──────────────────────────┘
                                │
      ┌─────────────────────────┼─────────────────────────┐
      ▼                         ▼                         ▼
┌───────────┐             ┌───────────┐             ┌───────────┐
│ AS500 DSL │             │  React    │             │    CLI    │
│ (terminal)│             │ + tables  │             │  prompts  │
└───────────┘             └───────────┘             └───────────┘
```

The config says: *"there is a `name` field of length 20 that's required, an `active` Y/N field with a cell renderer, and on delete the service needs the record id."* The renderer says: *"here's what that looks like in my world."*

Today only the terminal renderer exists (this is AS500, after all). But every non-presentational choice — field lengths, validators, access keys, paging semantics — lives in the config, so a second renderer can be added without touching a single existing config.

## 4. How it fits in AS500's dumb-terminal model

AS500 is built on the dumb-terminal pattern (see `CLAUDE.md`): the server owns everything; the client renders `rows: string[]` + `fields: Field[]` and sends keystrokes. CRUDTable is a server-side module that produces those same `rows`/`fields`/`navigation` payloads, so it fits the existing protocol without any bespoke channel.

The client doesn't know a CRUDTable screen from a hand-written one. All it sees is:

- A normal `ScreenResponse` with `rows`, `fields`, and a `navigation.list` block
- Standard keys (`ENTER`, `F3`, `F6`, `F12`, `PAGEUP/DOWN`)

This means every client-side improvement — keyboard row nav, mouse selection, shortcut keys — automatically benefits every CRUDTable screen.

## 5. Architecture at a glance

```
server/src/crudtable/
  types.ts      All config + context interfaces
  registry.ts   Stores configs; derives screen IDs
  context.ts    Namespaced persistence of CRUDContext in session.context
  runtime.ts    build/handle for list, form, delete-confirm screens
  router.ts     One-call integration hook for index.ts

server/src/configs/
  index.ts              registerCRUDConfigs() — called once at startup
  timeRegV2.ts          Example: per-day time entries with F7/F8 nav
  userMgmtConfig.ts     Example: admin user CRUD with role select + password
  roleDefaultsConfig.ts Example: composite-key permission CRUD
```

**Integration surface** — only three edits in `server/src/index.ts`:

1. Import `registerCRUDConfigs` and `handleCRUDScreen` / `buildCRUDScreenForResume`
2. Call `registerCRUDConfigs()` once in `startServer()`
3. The `default:` case in the main screen switch calls `handleCRUDScreen(...)` and only falls back to LOGIN if that returns `null`

Adding a new CRUD screen requires **zero** edits to `index.ts`.

**Screen-ID convention** — a `config.id` of `"things"` generates:

| Screen | ID |
|---|---|
| List | `CRUD_THINGS` |
| Form (create + edit) | `CRUD_THINGS_FORM` |
| Delete confirmation | `CRUD_THINGS_DELETE_CONFIRM` |

The `CRUD_` prefix guarantees no collision with manually-authored screen IDs like `LOGIN`, `MAIN_MENU`, `TIME_REG`.

## 6. The three screens at a glance

### List (`CRUD_{ID}`)

- Standard header + optional dynamic `listHeader(ctx)` text at row 5
- Subfile starting at row 7: `Opt` input column + one column per `columnBuilder` entry
- Page size 12. `PAGEUP/PAGEDOWN` for paging.
- Options: `2=Edit`, `4=Delete`, `9=OpenUI`, record actions from `5` upward (skip `9`).
- Status line auto-built from what's actually available (permissions-aware).
- Keyboard row nav + mouse selection are driven by the `navigation.list` block.

### Form (`CRUD_{ID}_FORM`)

- Header title becomes `CREATE {TITLE}` or `EDIT {TITLE}`.
- Rows built from `formBuilder` with labels at col 8, fields at col 30.
- `visible` / `disabled` / `required` expressions evaluated per render.
- `staticOptions` or `datasource` render as select dropdowns.
- `form.hint` appears as grey help text to the right of the field.
- Validation order: required checks → custom validators → service call.

### Delete confirm (`CRUD_{ID}_DELETE_CONFIRM`)

- Shows the record's fields (from `columnBuilder`).
- Single 1-char input; `Y` → perform delete, anything else → cancel.
- `Esc` / `F3` / `F12` cancel.

## 7. Mental models

CRUDTable's lineage and the flavour of its abstractions:

- **AS/400 DDS** — explicit field widths, fixed option numbers, Enter-to-act.
- **COBOL screens** — server owns state, client is a dumb renderer.
- **Terminal command graphs** — each screen is a state transition; `openUI` is a controlled jump that derives a new context.
- **A programmable admin runtime, not a form library.** Think "50 tiny screens declared as data" rather than "a React component that takes a schema."

If you're used to React admin libraries, the closest equivalent is **not** `react-admin`'s page-component model; it's closer to **Retool** or **Appsmith** — "here is a config; give me a working screen" — but with the config fully checked into source control as TypeScript.

## 8. What's portable across UIs, what's AS500-biased

Most of the config is already renderer-agnostic. A few fields carry a terminal bias that a second renderer should translate rather than honour literally:

| Field | Portability |
|---|---|
| `services`, `fieldConfigs.field/label`, `columnBuilder`, `formBuilder`, `actions`, `openUI`, validators, `BoolExpr`s, `datasource`, `staticOptions`, `requirePermission` | Fully portable |
| `FieldConfig.length` | AS500 needs it; a React table can use it as a max-width hint; a CLI can use it as an input max-length. |
| `FieldType` (`alpha`/`numeric`/`date`/`password`/`readonly`) | Map to `text`/`number`/`date`/`password`/`disabled` in a React form. |
| `form.uppercase` | React: `text-transform: uppercase` + uppercase on submit. |
| `form.hint` | Render as helper text next to the input. |
| `listHeader` returning `{row, col, content}` | A React port should treat the list as "extra header content" and ignore the coordinates. |
| `listKeys` (F-keys) | In React/CLI, surface as toolbar buttons or `:cmd` commands; the handler signature is already UI-agnostic. |
| `navigation.primaryAction` / `shortcuts` | Already abstract — keyboard-shortcut metadata. |

To build a second renderer, reimplement the build functions (`buildListScreen`, `buildFormScreen`, `buildDeleteConfirmScreen`). Everything below them — `loadContext`/`saveContext`, `callService`, `loadDatasources`, validation order — is renderer-agnostic and can be reused as-is if the transport is similar.
